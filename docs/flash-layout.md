# SPI flash 布局、HBA info 与解锁刷写的经过

来源：这张卡的 16MB flash 转储（`mvf_64 -rfb`）在不同时间点的对比。相关片段保存在 [data/](data/)，分析脚本在 [tools/](tools/)。

## 1. 16MB flash 的布局

flash 分成两个 8MB 的槽，槽 B（0x800000 起）的结构与槽 A 相同。`mnv_cli flash -t raw` 刷 7MB 镜像时写的是槽 A 的 0x000000–0x6FFFFF（**已验证**：刷后回读前 7MB 与镜像一致）。

| 偏移（槽 A） | 内容 | 可信度 |
|---|---|---|
| 0x000000 | 引导代码，ARM 向量表开头，代码是 Thumb-2 | 已验证 |
| 0x020000 | **生效的 HBA info**（512 字节，签名 `NEVOHBAF`） | 已验证 |
| 0x080000–0x0CFFFF | 主固件（字符串如 "raid_create RAID mode"、"No supported this OEM ID(0x%x)" 在 0xA9C6C、0xABFE8） | 已验证 |
| 0x200000 起 | 上述内容的另一份拷贝（0x220000 是一份 HBA info，0x280000 起是固件） | 已验证 |
| 0x600000 | UEFI option ROM（这张卡原有的内容就等于 `oprom_full.bin`，77824 字节） | 已验证 |
| 0x6FFFFC | 7MB 镜像的校验字：使整个 7MB 按小端 u32 求和为 0（`crc_fix.py`） | 已验证 |
| 0x750000 | 事件日志：`SPID` 头，之后是 `[SEQ]n[TIME]t[MSG]text` 文本记录 | 已验证 |
| 0x7D0000 | **OEM 数据块**（不在 7MB 镜像范围内，刷镜像不会改它） | 已验证 |

其他非空区域（0x40000、0x60000、0x100000、0x140000、0x180000、0x1C0000、0x1F0000、0x500000、0x710000、0x740000、0x780000 等）没有分析。

槽 B 里的对应位置：0x820000 和 0xA20000 各有一份 HBA info。

## 2. HBA info 结构（512 字节）

| 偏移 | 内容 |
|---|---|
| 0x00 | 签名 `NEVOHBAF` |
| 0x08 | `35 10 00 10`，含义未知 |
| 0x18 | `03 00 00 00`；0x1C：`00 02 00 00`（0x200，可能是长度） |
| 0x28 | **CRC**：`zlib.crc32(block[0x40:0x200]) ^ 0xFFFFFFFF`，按**大端**存 4 字节 |
| 0x3C | **求和校验**：小端 u32，使整个 512 字节按小端 u32 求和为 0 |
| 0x40 | `30 00 00 00` ×3：GPIO 功能开关/电平/值（`mnv_cli dumphba -a show` 显示 0x30） |
| 0x140 | `01 01 00 01`，含义未知 |
| 0x144 | 这张卡是 0x0F；默认副本和另一份旧备份里是 0x01。含义未知 |
| 0x148–0x15F | 每次卷配置变化都会变的字段（看起来每个卷一组），含义未知 |
| 0x1C8 | VID、DID（`4b 1b 41 22`） |
| 0x1CC | **SVID、SDID**：原厂是 `96 1b 00 40`（1b96:4000）；仓库的 `hbainfo.bin` 是 `4b 1b 41 22`（1b4b:2241） |

两个校验都**已验证**：对三个不同时间点的 HBA info 和 `hbainfo.bin` 都成立。脚本：[tools/an1500_f28b.py](tools/an1500_f28b.py)。

仓库的 `hbainfo.bin` 与这张卡刷写前的 HBA info 相比，只有四处不同：0x28（CRC）、0x3C（求和）、0x148–0x14F（易变字段）、0x1CC–0x1CF（子系统 ID）。也就是说，README 所说的"解锁"实质上就是把子系统 ID 从 WD 改成 Marvell 通用 ID。

固件会在卷配置变化时重写 0x20000 这一块（**已验证**：BIOS 建 RAID1 之后、命令行建 JBOD 之后，这一块的内容都变了）。

各份 HBA info 的情况（14:57 的转储）：

| 位置 | 子系统 ID | 0x144 | 说明 |
|---|---|---|---|
| 0x020000 | WD | 0x0F | 生效的那份 |
| 0x220000、0xA20000 | WD | 0x01 | 两份相同，像是出厂默认值 |
| 0x820000 | Marvell | 0x0F | 与仓库的 `hbainfo.bin` 逐字节相同；**刷写前就已经是这样**，原因不明 |

## 3. OEM 数据块（0x7D0000）

| 偏移 | 内容 |
|---|---|
| 0x00 | `"MNV "` |
| 0x04 | u16 0x0088（长度）；0x06：u16 0x000C |
| 0x08 | 4 字节，可能是校验（`e4 e2 cf 02`） |
| 0x0C | SVID、SDID：`96 1b 00 40`（WD） |
| 0x4C | 序列号，20 字节（`WUBT22230375`） |
| 0x60 | 型号，40 字节（`WD_BLACK AN1500`） |

`mnv_cli oemdata` 命令可以写这一块（**没有执行过**）。另一份旧备份 `an1500_backup.bin` 的 0x7D0000 也是同样的 WD 内容。

## 4. 解锁刷写的时间线（系统时间，2026-11-18）

| 时间 | 事件 |
|---|---|
| 13:58 | 完整备份 16MB，两次读取一致 → `an1500_backup_20261118.bin` |
| 14:00 | 用这份备份的前 7MB 做镜像：0x20000 写入 `hbainfo.bin`，0x600000 写入 `oprom_full.bin`；7MB 校验字不需要改（HBA info 自身求和为 0，option ROM 没变）。结果与 `an1500_backup_20241107_mod.bin` 逐字节相同 |
| 14:01–14:03 | `./flash_fw.sh an1500_20261118_mod.bin`（mnv_cli），约 2 分钟 |
| 14:04 | 回读：前 7MB 与镜像一致。此时 `mnv_cli info -o hba` 仍显示 SVID/SDID 为 WD（没有重启） |
| 14:10–14:39 | 用户关机，开机时在 BIOS 菜单里把卷改成 RAID1 |
| 14:46 | 检查：卷是 RAID1。**0x20000 的子系统 ID 已经变回 WD**，CRC 和求和校验也是按新内容重算过的。flash 其余部分与刷入的镜像相比只有事件日志不同 |
| 14:51 | 删除 RAID1，用 `mnv_cli create -r JBOD` 建两个 JBOD 卷 |

结果：flash 现在的内容是"解锁镜像 + 被固件改回 WD ID 的 HBA info"。因为 option ROM 原本就相同，所以代码部分与刷写前一致，卡等同于原厂状态。

## 5. 解锁为什么被还原（未查清）

两个假设，都**没有验证**：

1. **固件用 OEM 数据块里的子系统 ID 覆盖 HBA info。** OEM 块在 7MB 镜像之外，一直是 WD 的 ID；固件里有 "No supported this OEM ID" 字符串，mnv_cli 有专门的 `oemdata` 命令写 SVID/SDID。
2. **固件把内存里的旧 HBA info 写回了 flash。** 刷写时固件还在用刷写前读入内存的那份（WD ID），之后任何一次保存（关机、改卷配置）都会把它写回 0x20000，覆盖刚刷进去的内容。

区分两者的办法（都有风险，需要用户同意）：只改 0x20000 这一块后立即断电重启再读；或者用 `mnv_cli oemdata` 改 OEM 块。

**目前没有必要做**：在原厂 ID 下 JBOD 已经可以创建（见 [protocol.md](protocol.md)）。我没有观察到"解锁生效"的状态，所以也不知道解锁后卡的行为有什么不同。

## 6. 事件日志里的时间

- 日志时间戳来自主机设置的时间：mnv_cli 每次启动都发一条设置时间命令（见 [protocol.md](protocol.md) 2.1）。
- **时间戳不可靠，不要用来推断先后**。两个对不上的地方：
  - BIOS 里那几条记录换算出来是 14:46–14:49（当作 UTC 读）或晚 8 小时，而系统记录的关机到开机是 14:10–14:39。
  - 序号 105 的时间戳换算为 14:50:55，但包含它的转储是 14:47 之前读的。
- 14:57 的日志片段保存在 [data/eventlog_0x750000.txt](data/eventlog_0x750000.txt)。按顺序看：序号 99–103 是用户在 BIOS 里删除旧卷、建 RAID1；107–109 是 14:51 的删除和两次 JBOD 创建。
- 序号 105–106（一次 NVMe shutdown 和重新上线）发生在 BIOS 操作之后、14:46 的转储之前，触发原因没有查。

## 7. 固件逆向的零散线索（未深入）

- 引导代码里 0x13AF0 处有常量 `0x40001B96`（WD 的 SDID:SVID），后面跟着 `01 01 41 22 4b 1b …`。
- 主固件 0x8D51C 处有默认的 `4b 1b 41 22 96 1b 00 40`（VID、DID、SVID、SDID）。
- 引导代码的装载基址可能是 0xE0450000（由指针 0xE0464B10 一类的值推测，**未验证**）；主固件的装载基址没有找到。
- 反汇编方法：`docs/tools/dis.sh <dump> <起始偏移> <长度> thumb`。
